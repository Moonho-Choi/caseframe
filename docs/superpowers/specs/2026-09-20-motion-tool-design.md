# 교정 진행 영상 도구 (caseframe.kr/motion) 설계

작성일: 2026-09-20
상태: 구현 완료, 공개 대기 (2026-09-21)

## 1. 목적

같은 방향으로 찍은 교정 진행 사진(예: 상악 교합면) 여러 장을 넣으면,
사진 사이를 치아가 미끄러져 가듯 이어 주는 영상(MP4)을 브라우저 안에서 만든다.
환자 설명용이며, 이음턱편한치과 교정연구회 회원이 각자 진료실 PC에서 쓴다.

원형은 2026-09-20 맥에서 만든 파이프라인이다
(`~/이음랩/rife/align.py`, `morph.py`, rife-ncnn-vulkan). 그 결과와 같은 품질을 목표로 한다.

## 2. 원칙

- 사진은 사용자 컴퓨터 밖으로 나가지 않는다. 모든 계산은 브라우저 안에서 한다. (caseframe.kr 공통 원칙)
- 서버, 로그인, 저장 기능 없음. GitHub Pages 정적 파일만으로 동작한다.
- 한 번에 한 방향 한 묶음만 처리한다. 사진 고르기는 사용자가 한다.
- 인공지능이 안 도는 환경에서도 결과는 나온다(단순 겹치기로 자동 전환).

## 3. 하지 않는 것

- 사진 종류 자동 분류(환자 폴더 통째로 넣기)
- 완성 영상을 웹에 올려 환자에게 링크로 보여 주기 (별도 과제)
- 하악·정면 등 여러 방향 동시 처리
- 원근 보정 (맥 실험에서 24구간 중 18구간이 나빠져 제외)
- 빨강·파랑 표시색으로 방향 판정 (우리 치과 기구 전용이라 제외)

## 4. 화면 흐름

주소: `caseframe.kr/motion`, 제목 "교정 진행 영상". 한 화면, 위에서 아래로.

1. **사진 넣기** — 끌어다 놓기 또는 파일 선택. JPG/PNG/WebP. 한 번에 최대 40장.
   파일 이름의 8자리 날짜(YYYYMMDD)로 정렬, 없으면 파일 이름 순.
   HEIC는 "JPG로 바꿔 넣어 주세요" 안내.
2. **사진 줄** — 작은 그림 한 줄. 끌어서 순서 바꾸기, 빼기, 좌우 뒤집기 버튼.
   방향 검사(§5.2)에서 뒤집힌 것으로 판정된 사진은 자동으로 뒤집고 노란 경고 표시. 사용자가 되돌릴 수 있다.
   구도 맞추기 실패 사진은 회색 표시(§6).
3. **설정** — 세 가지만.
   - 품질: 빠르게 / 고품질 (기본: 고품질, 인공지능 불가 환경에서는 빠르게로 고정)
   - 한 단계 시간: 0.5~2.0초 (기본 1.2초)
   - 글씨: 켜기 / 끄기 (기본 켜기). "시작", "3개월", "1년 2개월" 형식. 날짜가 없는 묶음은 글씨 자동 끄기.
4. **만들기** — 진행 막대에 단계와 개수 표시("구도 맞추는 중 3/25", "중간 그림 12/24", "영상 만드는 중"). 취소 버튼.
5. **결과** — 화면에서 재생. "MP4 저장" 버튼. 파일 이름은 첫 사진 이름의 첫 토막 + `_교정진행.mp4` (예: `임희진_교정진행.mp4`).

## 5. 속 구조 (부품 6개)

모든 부품은 "사진 묶음(같은 크기의 화면 그림 배열)을 받아 사진 묶음을 돌려준다"는 같은 모양이다.
부품은 각각 별도 파일(`motion/js/*.js`)로 두고, 화면 코드(`motion/index.html`)는 부품을 순서대로 부르기만 한다.

### 5.1 읽기·정렬 (`load.js`)
- 파일 → 이미지 → 가로 1280(짝수)으로 축소, 첫 사진 비율에 맞춰 검은 여백.
- 날짜 추출: 파일 이름에서 `20\d{6}` 첫 일치. 정렬 키 = 날짜, 없으면 이름.
- 출력: `{name, date, canvas}` 배열.

### 5.2 방향 검사 (`orient.js`)
- 사진 한 장만 떼어 놓고 "뒤집혔나"를 절대적으로 판정하는 건 불가능하다(거울상도 그 자체로는 멀쩡해 보인다).
  잴 수 있는 건 두 사진 사이의 **상대 방향**뿐이므로, 상대 관계를 사슬로 이어 붙여 판정한다.
- 작업 해상도 가로 640으로 줄인 사본에서 ORB 2000점으로 검사한다(정밀 정합이 아니라 방향만 보면 되므로).
- 사진마다 정방향 특징점 F[i]와 좌우 뒤집은 특징점 FF[i]를 뽑고, 앞선 이웃 j(i−1, i−2)마다
  so = k(F[j], F[i]), sf = k(F[j], FF[i])를 잰다(k = RANSAC 내점 수).
- **판정 문턱은 한 가지다**: 한쪽 점수가 다른 쪽의 1.3배를 넘고 그 자체도 `REL_MIN = 8` 이상이면
  그 이웃과의 관계를 "반대" 또는 "같음"으로 읽는다. 아니면 그 이웃은 표를 못 던진다.
  (계획서 Global Constraints의 "반전은 15점 이상" 항목을 8점 하나로 바꾼 것이다 —
  실제 사진에서 짝짓기 점수가 10~50점 수준이라, 25장 중 6장만 고른 성긴 묶음에서는
  "정방향 0점 대 뒤집힘 9점"처럼 명백한 관계까지 15점 문턱에 걸려 놓쳤다. 2026-09-21 개정.)
- 첫 장을 기준(라벨 0)으로 놓고 상대 관계를 이어 붙여 각 사진의 라벨을 정한다. 이웃이 여럿이면
  짝짓기 점수를 표의 무게로 삼아 다수결한다.
- 라벨 0/1 중 어느 쪽이 정방향인지는 다수결로 정한다 — 뒤집힌 쪽이 과반이면 전체를 되뒤집는다.
- 어느 이웃과도 관계를 못 읽은 사진은 앞 사진과 같은 방향으로 두고 "다른 방향 사진일 수 있음" 경고(뒤집지 않음).
- 사진을 더 넣었을 때는 판정을 **새로 들어온 사진에만** 적용한다. 이미 화면에 있던 사진과
  사용자가 ⇄로 직접 고친 사진(`userFlipped`)은 그대로 둔다. 이번 투표에서 기준 방향의 부호가
  지난번과 반대로 잡히면(기존 사진 과반이 "뒤집어라") 새 사진에는 부호를 되돌려 적용한다.

### 5.3 구도 맞추기 (`align.js`) — 맥 `align.py` 최종 방식 그대로
- 특징점: opencv.js의 ORB(6000점). 작업 해상도 가로 1400 → 1280이므로 원본 그대로.
  (opencv.js 기본 빌드에 SIFT가 없어 계획서 Tech Stack대로 ORB를 썼다.)
- 쌍 변환: 유사변환(이동·배율·회전) RANSAC. 비율 0.7, 0.8 두 번 시도, 내점 8개 이상.
- 건전성 검사: 배율 0.6~1.6, 회전 20° 미만, 이동 가로의 50% 미만. 실패 시 무시.
- 앞의 최대 3장과 비교해 내점이 가장 많은 쪽에 붙인다. 모두 실패하면 밝기 패턴(ECC 유클리드)으로 시도, 그것도 실패하면 이동 없이 둔다(회색 표시).
- 미세 조정: 가운데 영역 마스크(세로 5~95%, 가로 12~88%)로 ECC 아핀. 조정 전후 중 정규화 상관이 높은 쪽 채택.
  - (2026-09-21 개정) ECC 아핀 결과를 가장 가까운 유사변환으로 투영해 형태를 보존한다(가로세로 비율·전단 0). 실사진 25장 실험: 아핀 그대로는 6장이 11~20% 비등방 변형, 투영하면 변형 0에 이웃 일치도 평균 0.707→0.723.
- 기준 틀: 전체 변환의 배율·기울기·중심 위치 중앙값으로 만든 "중간 구도".
- 출력: 기준 틀로 옮긴 사진들. 가장자리 5% 잘라내고 비는 곳은 가장자리 색으로 채움.
  잘라낸 크기는 가로·세로 모두 **16의 배수로 내림**한다(1280×854 → 1152×768). RIFE가 내부에서
  화면을 여러 번 반으로 줄이므로 16의 배수가 아니면 추론이 실패하거나 가장자리가 어긋나고,
  H.264 인코더에도 16의 배수가 안전하다.

### 5.4 밝기·색 맞추기 (`color.js`)
- LAB 색공간에서 채널별 평균·표준편차를 전체 중앙값에 맞춘다. 맥 `morph.py` 방식 그대로.

### 5.5 중간 그림 (`interp.js`)
- 모델: 공개된 RIFE ONNX(`motion/models/rife_fp32.onnx`, huggingface FuryTMP/RIFE_fp32, 21.6MB, MIT).
- 실행: onnxruntime-web 1.22(`vendor/ort/ort.webgpu.min.mjs`, wasm은 `/vendor/ort/`)로 WebGPU에서 돌린다.
  WebGPU가 없으면 wasm(CPU)으로 돌리지 않고 단순 겹치기로 전환한다. (CPU는 너무 느려 실용성이 없음)
  `navigator.gpu`는 화면을 열 때 확인해, 없으면 품질을 "빠르게"로 고정·비활성화하고 그 자리에 이유를 적는다.
  추론이 도중에 한 번이라도 실패하면 경고를 한 번 남기고 남은 구간을 단순 겹치기로 이어 간다.
- 세션은 한 번 만들어 계속 돌려 쓴다(만들기를 누를 때마다 21.6MB 모델을 새로 올리지 않는다).
- 시간 간격 t(0~1)마다 한 장. 초당 30장 기준.
  - 고품질: 모든 장을 인공지능이 그림.
  - 빠르게: 한 구간을 이진 분할할 때 **위 2단계만** 인공지능(= 한 구간을 4토막 낸 데까지),
    그 아래는 두 인공지능 그림의 선형 겹치기. (계획서 Global Constraints의 "4구간만 인공지능"과 같은 규칙.)
  - 단순 겹치기(전환): 인공지능 없이 앞뒤 사진 선형 겹치기.
- 메모리: 한 쌍씩 처리하고 결과는 곧바로 6번 부품(영상 인코더)에 넘겨 버린다. 전체 프레임을 쌓아 두지 않는다.
  사진 → CHW(float32) 변환도 쓸 차례가 된 두 장만 만들어 두고 쓴 것은 바로 버린다(40장 기준 425MB → 약 21MB).

### 5.6 글씨·영상 파일 (`encode.js`)
- 글씨: 각 프레임 왼쪽 위에 반투명 검은 띠 + 흰 글씨. 사진 i의 날짜 − 첫 날짜 → "시작" / "N개월" / "N년 M개월". 넘어가는 구간에서는 앞 사진 글씨 유지.
- 인코더: WebCodecs VideoEncoder(H.264, avc1) + mp4 muxer(`vendor/mp4-muxer.mjs`). 가로 1152(잘라낸 크기), fps는 §5.5의 planTiming.
- WebCodecs가 없으면 **지원하지 않는다** — "크롬이나 엣지를 써 주세요"로 안내하고 만들기를 멈춘다.
  (MediaRecorder + WebM 예비 경로는 2026-09-21에 지웠다: 사파리 16.4+·파이어폭스 130+도 VideoEncoder가
  있어 그 경로가 실제로 골라진 적이 없고, 골라졌다면 실제 시계로 녹화해 영상 길이가 몇 배로 늘어났을
  — 브라우저에서 한 번도 돌려 본 적 없는 코드였다.)
- 마지막 사진은 1초 정지 후 끝.

## 6. 잘못될 때

| 상황 | 처리 |
|---|---|
| 사진 2장 미만 | 만들기 버튼 비활성, 안내 |
| 크기·비율 제각각 | 첫 사진 비율로 맞추고 여백 채움 (오류 아님) |
| HEIC | 안내 후 해당 파일 무시 |
| 다른 방향 사진 섞임 | 사진 줄에 경고, 만들기는 허용(사용자 판단) |
| 구도 맞추기 실패 | 해당 사진 이동 없이 사용, 회색 표시 |
| WebGPU 없음 / 모델 로드 실패 | 단순 겹치기로 전환. WebGPU 없음은 화면을 열 때 품질을 "빠르게"로 고정, 결과 화면에 "이 컴퓨터에서는 빠른 방식으로 만들었습니다" |
| 추론 도중 실패 | 경고 한 번 남기고 남은 구간은 단순 겹치기로 계속 |
| WebCodecs 없는 브라우저 | 지원 안 함 — "이 브라우저는 영상 저장을 지원하지 않습니다. 크롬이나 엣지를 써 주세요." |
| OpenCV 30초 안에 준비 안 됨 | "OpenCV를 불러오지 못했습니다. 새로고침해 주세요." |
| 40장 초과 | 앞 40장만 받고 안내 |
| 취소 | 계산 중단(구도 맞추기·색 맞추기·프레임 만들기 모든 단계에서), 사진 줄과 설정 유지 |
| 만드는 중 사진 조작 | ◀▶⇄✕·끌기·사진 넣기 모두 잠금 |

## 7. 검사

1. 맥 결과와 비교: 2026-09-20 선별 25장(`~/이음랩/rife/사진_선별/`)으로 웹 도구 실행. 구도는 이웃 사진 일치도(맥 0.684)와 비교, 영상은 나란히 눈으로.
2. 방향 검사: 25장 중 3장을 일부러 뒤집어 넣어 경고와 자동 복구 확인.
3. 진료실 윈도우 PC 크롬에서 고품질 모드 소요 시간 측정. 5분 초과면 기본값을 "빠르게"로.
4. 사파리·파이어폭스에서 "크롬이나 엣지를 써 주세요" 안내가 뜨는지 확인(WebM 저장은 하지 않는다).
5. 사진 2장, 40장, HEIC 포함 묶음으로 §6 처리 확인.

## 8. 만드는 순서

가장 불확실한 것부터.
1. RIFE ONNX 변환 + 브라우저 WebGPU 실행 시험 (안 되면 대체 모델 결정)
2. opencv.js 특징점·RANSAC·ECC 가용성 시험 (SIFT 없으면 AKAZE)
3. 부품 5.1~5.6 각각 만들고 맥 결과와 대조
4. 화면 붙이기, §6 처리, §7 검사
5. 원장 GitHub Desktop 푸시 → caseframe.kr/motion 공개

## 9. 위험

- RIFE ONNX 변환 실패 가능 → 대체 모델. 품질 차이는 25장 비교로 확인.
- opencv.js에 SIFT 없을 가능성 → AKAZE. 대응점 수가 줄어 실패 사진이 늘 수 있음.
- 회원 PC 성능 편차 큼 → 시간 측정 후 기본값 조정.
- 모델 파일(20~40MB) 첫 로드 시간 → 진행 표시와 캐시.
